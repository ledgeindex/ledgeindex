# Crawl & retrieval

`@ledgeindex/core` — the **primitive layer**: crawl the web, extract markdown, chunk, embed, store, and query with optional reranking.

## When to use core

Use `@ledgeindex/core` when you need direct control over indexing and retrieval: custom crawl filters, your own chunking policy, a specific vector store, or embedding into an existing app without the full HTTP server.

If you only want a structured site brief (identity / pricing / capabilities), prefer [Site research](/docs/profile) or SDK [`profile`](/reference/sdk/profile). If you want crawl + ask without composing core yourself, prefer [CLI](/docs/cli) or [SDK](/docs/sdk). If you want ingest + chat routes out of the box, prefer [HTTP server](/docs/server) with the `docs` profile ([Sources, chat & MCP](/docs/docs-profile)).

## Quickstart

Create a shared runtime context once, then call the stage APIs you need:

```ts
import { createCoreContext } from "@ledgeindex/core";

const ctx = await createCoreContext({
  // dataDir, embedder, stores, logger, …
});
```

Install:

```bash
npm i @ledgeindex/core
```

Typical flow after context exists:

1. Crawl / discover URLs for a source
2. Extract HTML → markdown
3. Chunk + embed via the chunk pipeline
4. Query with your vector / catalog helpers

Visit [Pipeline stages](/docs/core/pipeline) for the stage map.

## Use core

Import from the package root for common helpers, or from stage paths for focused modules:

```ts
import { chunkMarkdown, createCoreContext } from "@ledgeindex/core";
import { parsePage } from "@ledgeindex/core/extract/parser/extract-content.js";
```

`createCoreContext` wires shared services (stores, embedder, logger) that pipeline helpers expect. Prefer one context per process rather than constructing stores ad hoc in every call site.
